# 财税 Agent Harness 开发与审查规划

依据：用户提供的“财税 Agent Harness 系统设计与实现”赛题截图。

资源配置：**两份 Claude Pro 统一用于开发，一份 OpenAI Plus 用于独立审查**。Claude / Opus 5.5 负责全部前后端、界面设计、测试、修复与交付；GPT‑6.1 Sol（本聊天助手）仅负责审查。Claude 保持统一项目与开发流程，不按账号拆分角色或版本。本文是待执行的规划，尚未调度模型或开始实现；接入时核对实际模型权限与标识。

## 1. 项目目标与完成定义

交付一个可以运行、演示和核查的财税任务处理系统：用户连续交代查询、补充、保存和检查任务，系统能记住进度、找到适用规则、调用工具完成操作，并准确说明结果。

完成定义：

1. 发票与银行查询、补充信息并保存、多轮检查三个场景，使用同一个运行循环并形成完整闭环。
2. 任务进度、长期偏好、规则文档分别管理；企业、用户、月份与对象绑定清楚，不串用信息。
3. 保存前完成校验，保存后回读核验；失败、结果未知与成功能够区分，重复提交不产生重复写入。
4. 用户可以查看结果、操作记录、记忆和规则来源，并管理记忆与规则。
5. 提供源码、启动说明、设计说明、固定评测集、评测结果和可复现 Demo。

**首版范围**：少量模拟数据、一个业务 AI 助手、顺序执行、本地可运行。开发由 Claude 统一承担，关键里程碑由 GPT‑6.1 Sol 独立审查。计划按 7 个里程碑推进，根据实际额度安排工作批次。

## 4. 总体架构与技术选择

### 4.1 系统链路

```text
用户 / 演示页面
       ↓
API：取得已绑定的用户、企业、月份与会话范围
       ↓
Harness：加载任务 → 构建上下文 → 选择下一步 → 检查动作 → 执行 → 更新状态
       │                  │                         │
       │             Memory / Knowledge        Tool Gateway
       │                  │                         │
       └──────────── SQLite 持久化 ─────────── 模拟业务接口
                          ↓
              保存回读、操作记录、结果展示
```

模型提出受约束的动作，程序检查动作是否允许执行。企业和用户身份、权限判断、状态迁移、重复写入控制和保存核验由程序负责。

### 4.2 首版技术栈

以下为候选方案，由 Claude 结合实际材料确定并实现，审查时核对其是否满足需求和运行条件。

| 层 | 方案 | 目的 |
|---|---|---|
| 服务端 | Python + FastAPI + Pydantic | API、数据约定和输入输出校验 |
| 存储 | SQLite + 明确的迁移脚本 | 少量业务数据、任务、记忆、规则和操作记录 |
| 规则检索 | 元数据过滤 + 中文关键词/短语匹配 + 返回原文片段 | 小规模规则集可解释、易核查 |
| 业务工具 | 统一工具网关 + 可替换的模拟接口适配器 | 后续接入主办方接口时保留运行流程 |
| 页面 | 建议 React + TypeScript，具体组件、样式与交互实现由 Opus 5.5 决定 | 展示对话、实际结果和操作记录 |
| 测试 | 服务端行为测试 + 关键页面操作检查 + 多轮评测脚本 | 覆盖主链路、隔离、失败与恢复 |
| 模型接入 | 独立 Provider Adapter，模型名与凭证通过环境配置 | 按实际可用接口接入业务运行模型 |

FastAPI 的响应模型可用于输出校验与字段过滤；业务正确性仍通过应用逻辑和测试保证。[官方说明](https://fastapi.tiangolo.com/tutorial/response-model/)

本地模拟业务写入使用 SQLite 事务组织提交与回滚。跨外部接口的操作通过操作标识、状态查询和回读核验协调，不能把本地事务当作外部业务的一次性执行保证。[SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)

开发时锁定实际验证过的依赖版本。首版先完成上述链路；语义检索仅在固定规则检索样例暴露不足时纳入后续迭代。

## 5. 核心设计

### 5.1 统一运行循环

每轮处理：

1. 从服务端取得当前用户与授权范围，加载任务的企业、月份、对象及未完成事项。
2. 接收本轮消息，将明确补充或更正的内容写入任务状态。
3. 检索相关记忆与有效规则，读取必要的业务数据，形成有长度预算的上下文。
4. 模型返回结构化动作：查规则、查数据、追问、提出修改、执行已授权修改、核验或结束。
5. 程序校验动作参数、范围、权限及前置条件，通过后执行工具。
6. 持久化工具结果与任务进度；涉及保存时进入核验，再生成面向用户的回复。

三个场景只改变任务目标、工具参数和完成条件，共用上述循环。单轮设步骤预算；达到预算时保留状态并说明停在哪一步，避免无限调用。

任务状态拟定为：`running`、`waiting_user`、`waiting_tool`、`verifying`、`completed`、`failed`。操作结果另行记录为成功、失败、处理中或结果未知，避免用任务状态掩盖一次工具调用的不确定性。

### 5.2 记忆分层与范围隔离

| 类型 | 内容 | 管理方式 |
|---|---|---|
| 任务记忆 | 当前目标、已查对象、缺失信息、候选修改、待核验操作、下一步 | 随任务持久化，跨轮恢复 |
| 长期偏好 | 用户明确要求记住的称呼、输出习惯或适用业务习惯 | 支持查看、更正、删除与作用范围选择 |
| 对话摘要 | 已确认事实、来源、未完成事项及最近必要上下文 | 从结构化状态生成，并按来源变更重建 |

关键约定：

- 数据读取必须带授权范围。企业、用户、任务与业务对象都使用稳定 ID，名称只用于展示与检索。
- 长期偏好默认按用户与企业隔离；跨企业偏好仅在用户明确指定时建立。
- 切换企业后创建或恢复对应企业的任务，旧任务单独保留。新企业不能继承旧企业的对象选择与修改草稿。
- 切换月份采用同样的显式绑定；“上个月”“这张”等指代无法唯一确定时追问。
- 更正、删除记忆后，更新记忆修订号，并清除或重建相关上下文摘要；避免旧内容从摘要中重新进入模型。
- 可删除记忆的正文不复制进不可变操作日志。日志只保留变更类型与记录标识；正常业务操作凭证独立管理。
- 长期偏好不能覆盖工具权限、适用规则或本轮用户明确指令。

### 5.3 规则文档管理

每个规则版本至少包含：`document_id`、`version`、标题、原文、条款标识、业务类型、适用范围、适用时间和启停状态。

检索流程为：先按授权范围、业务类型、适用时间和启停状态过滤，再匹配内容。回答引用具体文档版本和条款片段。

更新规则时新增版本，保留历史版本以供追查。停用和更新后使相关检索结果与摘要失效；进行中的修改在保存前重新检查依赖规则。适用规则的时间口径按主办方材料配置，不简单把“最新版本”当作所有历史业务的适用版本。

找不到依据时说明缺少哪项依据；多个有效条款冲突时展示冲突并追问或暂停该项操作。规则材料和工具返回的文本作为业务数据处理，不能据其修改系统权限。

### 5.4 上下文组织

上下文按业务需要选取，不持续拼接全部聊天记录。必须保留：

- 当前企业、月份、用户和任务绑定。
- 已确认且仍有效的字段、业务对象 ID 与来源。
- 缺失信息、未完成事项、待核验操作。
- 当前适用规则片段及版本。
- 与本轮有关的长期偏好和最近必要对话。

摘要中的事实附带来源标识。规则、记忆或业务记录变更后，重新检索或读取受影响的信息。金额、状态和保存结果以最新工具读取为依据，不能仅从旧摘要推断。

### 5.5 工具写入与结果核验

统一工具结果至少返回：状态、数据、错误码、操作标识、是否允许重试，以及必要的记录版本。

写入流程：

```text
解析用户修改意图与授权
    → 确认企业、月份、对象与字段
    → 检查权限、规则和记录版本
    → 持久化修改草稿与稳定操作标识
    → 调用写入接口
    → 回读目标对象，核对字段与版本
    → 标记已核验完成，向用户说明结果
```

具体要求：

1. 用户已经明确要求保存，且对象与字段清楚时直接执行；缺少关键字段或对象不唯一时集中追问。
2. 每次业务修改先保存稳定的操作标识，重试沿用同一标识。模拟接口用唯一约束与事务控制重复提交；不同对象或不同修改内容不能复用该标识。
3. 只有回读到预期结果才标记完成。写入接口报成功但回读不符时，进入核验异常。
4. 写入超时或连接中断时先按操作标识查状态、再回读目标记录。未确认是否提交前，不无条件重发。
5. 外部接口缺少幂等或状态查询能力时，按可核实证据判断；证据不足则保留结果未知，不承诺任意接口都能自动避免重复写入。
6. 记录版本改变时重新读取、比较差异；若改变影响修改意图，则让用户确认变化后的对象与内容。
7. 程序重启后先恢复未完成操作并核对外部结果，再决定继续、等待或结束。

### 5.6 数据与公共接口约定

核心实体：`Task`、`TaskStep`、`Memory`、`RuleDocument`、`RuleVersion`、`Operation`、`AuditEvent`，以及模拟发票和银行流水。

公共约定优先锁定以下内容：

| 约定 | 必须明确的字段 |
|---|---|
| 任务范围 | tenant/user/company/task/object 标识、月份、授权范围 |
| 模型动作 | 动作类型、参数、所依赖的规则/记忆标识、必要的简短动作说明 |
| 工具结果 | 状态、结果、错误码、operation_id、重试条件、记录版本 |
| 规则引用 | document_id、version、条款标识、适用范围与时间 |
| 修改草稿 | 对象、原记录版本、拟修改字段、用户指令来源、operation_id |
| 操作记录 | trace_id、任务与步骤、工具、脱敏参数摘要、结果、耗时、引用来源 |

业务范围由服务端补入工具请求，模型输出不能任意重写用户身份或企业权限。过程展示保留动作与证据，不要求暴露模型内部推理。

## 6. 三个场景如何演示与验收

### 场景一：发票与银行查询

用户指定某企业、某月份，查询发票及银行收支，要求检查信息是否完整。

系统确认范围、读取数据、匹配规则，回答查询结果与缺失字段，并保存未完成事项。查询为空时返回空结果；对象不唯一时追问；缺少规则时不自行下结论。

**验收**：查询与企业、月份对应；规则引用可查；缺失项有对象 ID，后续能继续处理。

### 场景二：补充信息并保存

用户继续上一任务，为某张发票补充缺失信息并要求保存。

系统利用已有任务绑定定位对象，形成修改草稿，经校验后保存并回读。对象仍有歧义时追问。用户本轮补充的内容只更新对应对象。

**验收**：数据库真实变化与回复一致；修改对象正确；重复发送或恢复任务不产生重复业务写入。

### 场景三：多轮检查

用户询问“还有哪些没有处理”，途中更正信息、切换企业或恢复之前的任务。

系统使用任务状态与最新数据区分已完成、未完成、待核验事项；企业和月份切换后更新绑定；返回旧任务时恢复其进度。

**验收**：不遗忘待办、不带入其他企业的信息，已核验项目与待核验项目区分清楚。

## 8. 测试、评测与验收指标

### 8.1 固定回归集

计划先编写 30 个有明确预期的多轮案例，种子数据同时覆盖两个用户、两家企业、两个月份，并设置相同名称或相似编号的对象。

| 类别 | 数量 | 重点案例 |
|---|---:|---|
| 三场景主链路 | 6 | 正常查询；空结果；发现缺失；补充保存；继续检查；更正已有信息 |
| 记忆与范围隔离 | 6 | 用户切换；企业切换；月份切换；偏好更正；偏好删除；恢复旧任务 |

| 表达与完整性 | 4 | 先结果；失败说明具体；未确认保存时直说；引用与实际使用规则一致 |

真实模型调用分批安排：先用覆盖三场景的 6 个案例检查接入，再执行完整 30 例首轮评测。新增模型调用前先查看预算与失败原因，修复明确问题后才重跑受影响案例。确定性回归可直接由本地工具执行；模拟通过与真实模型通过分别统计。若运行时模型接口与用量尚未确定，保留真实评测待执行状态。
