# 设计说明（v0.3 · 2026-10-28）

## 1. 完成情况

**已完成（三个场景共用一套流程）**

- **统一运行循环**（`harness.run_turn`）：查询资料、补充保存、多轮检查不设固定分支。模型通过 tool calling 决定查询、追问、调用工具或结束；单轮最多 8 步，超出时停下并说明。
- **数据与工具**：Excel 导入 SQLite（金额存整数分），此后以库内当前数据为准。14 个工具：月度汇总、发票与流水查询、用途检查、规则检索与条文、修改发票、切换企业、任务记忆、长期偏好的增删改查。
- **知识库**：直接解析官方《业务规则》docx；支持导入、检索、更新（新增版本）、停用和启用，命令行和网页都可操作。
- **记忆**：任务记忆与待办账本按用户、企业隔离，每人每企业最多一个未完成任务（唯一索引保证）；长期偏好可查看、更正、删除；新会话接着处理上次的待办。
- **运行记录**：每轮记录完整模型输入、选用的记忆与规则、工具参数与结果、token 用量，过滤密钥；可导出 JSON 与 Markdown。
- **进阶**：长对话结构化摘要；规则变化后提醒重新检查；写入中断后启动时自动回读核对，不重复提交（`FH_FAULT=crash_after_commit` 可复现）。
- **验证**：283 项确定性测试；38 个多轮案例用真实模型评测，最近一次 114/114（每例 3 次），规则引用异常 0 条；一组规则解析对比实验（第 5 节）。数字与明细见 `docs/acceptance/report.md`。

**未完成**

- 写入只做回读核对，不自动重试；对接外部系统前，需要先确认对方支持按幂等键查询。
- 长对话摘要由程序按规则生成，没有用模型做语义压缩；轮数很多时，较早原话只保留前 40 个字。
- 没有登录与并发控制，演示入口直接选定用户，与赛题设定一致。
- 发票文件导入（PDF/OFD、扫描件识别、对话中上传）已实现但不在初赛范围，**默认关闭**（`FH_FILE_IMPORT=1` 开启），演示与评测结论不依赖它。

## 2. 模型与程序的分工

| 模型负责 | 程序负责 |
|---|---|
| 理解需求、指代与更正；判断用户是否要求修改、保存、记住 | 身份与权限：由会话入口绑定，工具不接受企业、用户参数，对话中无法更改 |
| 决定下一步：查、问、改，还是结束 | 金额汇总（整数分）、收入与支出分开统计 |
| 从原话中摘取用途、备注和偏好内容 | 适用规则解析：按企业、业务日期、启用状态选版本，并列出被排除的版本及原因 |
| 组织回复，引用工具返回的规则版本 | 用途检查（按规则参数里的金额门槛）、字段白名单、幂等写入、写后回读、待办更新 |
| | 核对模型给出的证据：原话出处、对象与内容的对应（第 4 节） |

**理由**：赛题里最常见的错误——算错金额、用了停用规则、写错企业、重复写入、没核验就说已保存——都能用确定性方法验证，所以交给程序并用测试锁住。理解自然语言、判断该做什么、把结果讲清楚，是程序做不好的部分，交给模型。

## 3. 记忆与知识管理

| 类型 | 存放与范围 | 进入模型输入的方式 |
|---|---|---|
| 任务记忆 | `tasks`，用户 + 企业，最多一个未完成 | 目标、关注月份、待处理与已核验的发票、所依据的规则版本 |
| 待办账本 | `open_items`，跟随任务 | 由检查结果写入；写后回读通过才标为完成 |
| 长期偏好 | `memories`，默认用户 + 企业，用户明确说明时跨企业 | 全部有效偏好带编号列出；删除时清空正文并把运行记录里的原文换成占位符 |
| 对话 | `messages`，会话 + 企业 | 只取当前会话、当前企业的最近消息，超出预算的部分换成结构化摘要；切换企业后旧企业的对话不再带入 |

**规则**按“编号 + 版本”保存适用企业、生效日期、状态、条款原文和程序参数（如用途必填门槛）。更新即新增版本，旧版保留；选版本时取“适用企业包含当前企业、生效不晚于业务日期、状态启用”中生效最晚的一版。每轮只把当前企业适用规则的目录放进系统输入，条款原文由模型调用工具取得；回复中引用的《规则名》x.x 版若不是本轮工具返回过的，会在运行记录中标为异常。

## 4. 自己的设计选择：模型决定，程序核对证据

赛题同时要求“不能用关键词匹配代替模型理解”和“按用户明确要求修改、不误报成功”。只靠模型，误写难以核对；靠关键词判断意图，又违背前一条。我们的做法是：**要不要做由模型决定，程序不猜意图，只核对模型拿出的证据**。

1. **出处**：写入工具必须带 `user_quote`，即用户原话的逐字摘录。程序在本次会话、当前企业的用户消息里找到这一句；上一会话的草稿、切换企业前的话、附件文件名都找不到出处。
2. **对象与内容**：只能改这句话点名的发票，写入的用途和备注必须是用户为这张发票、这个字段给出的原文；“F002 和 F003 分别填 A 和 B”按顺序逐一对应；原话说了月份时，发票的开票月份必须一致。没点名发票的确认（“可以了，保存吧”）只能指向紧挨着的上一句点名的发票，或上一句之后程序记下的待确认修改。
3. **风险表述只拦不放**：原话里有否定、条件、不确定、举例或是在询问时，程序不写入，而是记下待确认的修改，由模型逐项讲给用户；用户紧接着的下一句确认后才按记下的内容写入。这一小组表述只会让写入多一次确认，从不替模型决定“要写”。
4. **幂等**：幂等键包含来源消息，同一句话的重试不会重复写入；用户之后的新要求（包括改回旧值）是新的操作。

长期偏好用同样的方式：原话出自本轮，内容出自原话，跨企业须另外摘录用户说明适用范围的原话；要更正或删除的那条须能从对话中指认（编号、内容重合、上一轮回复刚说到，或只有一条）。查询月份也要能在原话或任务记忆里找到出处，否则工具返回 `MONTH_UNCONFIRMED`，让模型追问。

**效果示例**：新会话里只说“可以了，保存吧”不会执行上一会话的草稿（评测 M4）；模型从项目名称推出的用途找不到出处（`test_cannot_guess_purpose_from_item`）；“如果经理同意就把 F003 填快递”先列出待确认修改，用户下一句确认才写入（W2）。同类设计也用来减少无关追问和用错规则：用户只说“7月”时按最近的 7 月理解，不再追问年份；规则版本由程序解析，模型拿不到停用版本当依据。

## 5. 对比实验：规则由程序解析，还是交给模型挑

同一数据、同一模型（deepseek-flash）、同一提问，只改规则的提供方式：对照组把全部版本（含停用、未生效）交给模型自选；实验组由程序先选出适用版本。每题 5 次。

| | 程序解析 | 模型自选 |
|---|---|---|
| X1–X6：停用版本、1000.00 边界、规则更新、未来生效、新版停用后回退、只有空格的用途 | 30/30 | 30/30 |
| X7：已停用版本写着看上去最“适用”的内容——答对 / 指出冲突请用户确认 / 按停用版本作答 | 4 / 1 / **0** | 1 / 2 / **2** |
| 多报的发票（合计） | 0 张 | 8 张 |
| 平均输入 / 输出 tokens | 8,595 / 636 | 9,378 / 1,020 |
| 平均耗时（并发运行，仅供组间比较） | 5.7 秒 | 8.2 秒 |

另做了一组模型输入预算对比（对话历史 6000 字 vs 800 字，9 个多轮案例各 3 次）：两档都全部通过，输入只差约 2%。现有案例只有 2–3 轮，测不出差别，需要补长对话案例再比较，见验收报告第 7 节。

结论：常规题两组都能答对；碰到“已停用的版本写着看上去最对的内容”时，模型自选 5 次只答对 1 次、2 次按停用版本作答（2026-10-26 与 10-28 早些时候的两轮分别是 5/10、4/5），程序解析在结构上不会出现这种错误，输入更短、更快。样本较小，结论只针对该模型和这份数据。

## 6. 后续完善

- **长对话**：补充 10 轮以上、早期信息在后面被用到的评测案例，比较摘要与截断等输入方式；在结构化摘要之上，用模型对较早对话做带出处的语义压缩；任务记忆或规则变化时，让相关摘要失效并重新生成。
- **信息更新**：规则导入时做条款冲突检测（如 X7 这类停用版本与现行版本矛盾），提前提示管理员；数据被他人修改后，按版本号提示模型重新查询，而不是沿用旧结果。
- **任务恢复**：对接外部接口时，用幂等键先查询再决定是否重试，并单独区分“结果未知”状态，恢复后如实告诉用户。
