# 设计说明（v0.2 · 2026-10-26）

## 1. 完成情况

**已完成**

- **统一运行循环**（`harness.run_turn`）：查询资料、补充并保存、多轮检查三个场景共用一个循环，不设固定分支。由模型通过 tool calling 决定下一步：查询、追问、调用工具或结束。单轮最多 8 步，超过时停下并说明原因。
- **数据**：从 Excel 导入 SQLite，金额以整数分存储。此后以库内当前数据为准，原始 Excel 只在 `init` 时读取。
- **工具**：共 14 个，覆盖金额汇总、发票与流水查询、用途检查、规则检索、修改发票、切换企业、任务记忆、长期偏好的增删改查。
- **规则知识库**：直接解析官方《业务规则》docx。支持导入、检索、更新（新增版本）、停用和启用，可在命令行或网页上操作。
- **记忆**：任务记忆与待办账本按用户、企业隔离；长期偏好可以查看、更正、删除；新开会话后能接着处理上次的任务。
- **运行记录**：每轮记录完整的模型输入、模型输出、工具参数与结果、选用的记忆与规则、token 用量，并过滤密钥。支持导出为 JSON 和 Markdown（`runs export`）。
- **中断恢复**：写入时先登记“打算写成什么”。如果在提交后、回读前中断，下次启动会自动回读核对，标记成功或不一致，并写进任务记忆，下一轮如实告诉用户。不会重新提交。可以用 `FH_FAULT=crash_after_commit` 复现这个场景。
- **长对话**：超出预算的较早对话会换成程序生成的结构化摘要，包括用户较早的要求和本会话已核验的保存（附操作号），不会直接丢弃。
- **规则变化提醒**：如果待办所依据的规则版本和现在适用的版本不同，会提示模型重新检查，并告诉用户结果有什么变化。
- **演示入口**：演示网页（首屏有概览，有运行记录、当前数据、规则管理三个面板），也可以用命令行。
- **验证**：42 项确定性测试；24 个多轮案例用真实模型评测；一组规则解析对比实验。数字见 `docs/acceptance/report.md`。

**未完成**

- 写入流程只做回读核对，不会自动重试。对接外部接口时，还需要先确认对方是否支持按幂等键查询。
- 长对话摘要按规则生成，没有用模型做语义压缩。对话轮数很多时，较早的细节只保留原话的前 40 个字。
- 没有登录和多用户并发，由演示入口直接选定用户，这和赛题设定一致。

## 2. 模型与程序的分工

| 模型负责 | 程序负责 |
|---|---|
| 理解需求、指代和更正 | 身份与权限：会话入口绑定，对话中无法更改 |
| 决定下一步：查、问、改，还是结束 | 金额汇总：Decimal 加整数分，收入和支出分开统计 |
| 从用户原话中摘取用途和备注 | 适用规则解析：按企业、业务日期、启用状态选版本，并说明被排除的版本及原因 |
| 判断用户是否明确要求保存 | 用途检查：按规则参数里的金额门槛执行，等于门槛也算必填 |
| 组织回复，引用工具返回的规则版本 | 字段白名单、发票唯一定位、幂等写入、写后回读、待办状态更新 |
| 识别用户要求记住的偏好 | 记忆的范围隔离，删除时清空正文，上下文预算 |

**为什么这样分。** 赛题里最容易出错的几件事都可以用确定性的方式验证：金额算错、用了已停用的规则、写错企业、重复写入、未核验就报成功。所以这些全部交给程序，并由测试锁住。模型只负责程序做不好的部分，也就是理解自然语言、判断该做什么、把结果讲清楚。

工具在结构上就不接受企业和用户参数，范围由服务端注入；写入工具只开放用途和备注两个字段。这样即使模型理解错了，也无法越权或写错对象。

## 3. 记忆与知识管理

| 类型 | 存放 | 范围 | 进入模型输入的方式 |
|---|---|---|---|
| 任务记忆 | `tasks`，每个（用户, 企业）最多一个未完成任务，有唯一索引保证 | 用户 + 企业 | 目标、关注月份、待处理和已核验的发票、已确认的事实 |
| 待办账本 | `open_items` | 跟随任务 | 由检查结果写入；只有写后回读核验通过才标为已完成 |
| 长期偏好 | `memories` | 默认用户 + 企业；用户明确要求时才跨企业 | 全部有效偏好附带编号，模型可以更正或删除 |
| 对话 | `messages` | 会话 + 企业 | 只取当前会话、当前企业的最近消息；切换企业后，旧企业的对话不再带入 |

- **删除偏好**：正文清空，同时把运行记录里保存的该段原文替换成占位符，删除的内容不会再进入任何模型输入。
- **规则**：每个版本都保存编号、版本、适用企业、生效日期、状态、条款原文和程序参数（如用途必填的金额门槛，导入时从正文解析，也可以手动指定）。更新规则就是新增一个版本，旧版本保留。选择版本时取“适用企业包含当前企业、生效日期不晚于业务日期、状态为启用”中生效最晚的那个。
- **规则引用检查**：回复里出现的《规则名》x.x 版，如果不是本轮工具返回过的版本，会在运行记录中标为异常。

## 4. 自己的设计选择：修改授权必须有“出处”

赛题有三条容易混淆的要求：只查询不代表授权修改；新开对话不代表获得修改授权；不能根据销售方或项目名称猜测用途。

如果靠关键词判断（例如看用户有没有说“保存”），会违反“不能用关键词匹配代替模型理解”。如果完全交给模型，又难以核对。

我们的做法是**由模型判断，由程序核验出处**：

1. 调用 `update_invoice` 时必须附上 `user_quote`，即用户要求修改的原话。程序检查这句话是否确实出现在**本次会话**的用户消息里。
2. 写入的用途和备注文本，也必须能在本会话的用户原话中找到。

效果如下：

- 上一会话留下的“草稿”拿不出本会话的原话，自然无法执行。评测案例 M4 中，新会话里只说“可以了，保存吧”时，没有发生写入。
- 模型从项目名称推测出来的用途，无法通过出处校验（测试 `test_cannot_guess_purpose_from_item`）。
- 程序不解析意图，只核对证据；是否要保存仍由模型理解。

长期偏好用同样的机制，必须附上用户要求记住的原话；查询时的月份也要能在用户原话或任务记忆中找到出处，否则工具会返回 `MONTH_UNCONFIRMED`，让模型去追问。

## 5. 对比实验：规则由程序解析，还是交给模型挑？

实验设置：同一份数据、同一个模型（deepseek-flash）、同样的提问，只改变规则的提供方式。

- **对照组**：把所有规则版本（含已停用、未生效的）原样交给模型，由它自己判断用哪一版。
- **实验组**：程序先按企业、业务日期、启用状态选出适用版本，再交给模型。

| 题目 | 程序解析 | 模型自选 |
|---|---|---|
| X1–X6：版本陷阱、1000.00 边界、规则更新、未来生效、新版停用后回退、只有空格的用途 | 30/30 | 30/30 |
| X7：已停用的版本写着最“适用”的内容（条文相互冲突）：答对 / 指出冲突 / 答错 | 8 / 2 / 0 | 1 / 4 / **5** |
| 平均输入 token（X6–X7 这一轮） | 6,996 | 10,880 |

结论：常规场景下，模型自己挑规则也能答对。但碰到“已停用的版本写着看上去最对的内容”时，有一半的次数它会照着已停用的规则作答，而程序解析在结构上就不会出现这种错误，同时还更省 token。样本较小（每格 5–10 次），这个结论只针对该模型和这份数据。

## 6. 后续完善

- **长对话**：在结构化摘要的基础上，用模型对较早的对话做带出处的语义压缩。任务记忆或规则一旦变化，就让相关摘要失效。
- **外部接口**：对接真实业务系统时，用幂等键先查询再决定是否重试，并单独区分“结果未知”的状态。
- **规则**：支持条款之间的冲突检测（例如 X7 这种情况），在导入规则时就提示管理员，而不是等到回答问题时才发现。
