## 1. 赛题要点（只列影响实现的部分）

**三个场景共用一套流程**

| 场景 | 必须做到 |
|---|---|
| 查询资料 | 按企业、月份查询发票总额、银行收入、银行支出，三者分别统计，不相互抵减；引用适用规则名称和版本 |
| 补充并保存 | 确认企业、发票、修改内容和权限 → 保存 → 再查询核对；只改用途、备注 |
| 多轮检查 | 记住企业、月份和未完成事项；用户补充后继续处理并更新结果 |

**数据与权限**

- 企业 C001 甲企业、C002 乙企业。用户 U001 对两家企业都可查看、可修改；U002 只能查看甲企业，不能访问乙企业。
- 权限由演示入口选定用户后由程序校验，**对话不能更改身份或权限**。
- 发票由 `(企业编号, 发票编号)` 定位，同一编号在两家企业都存在（F001–F020）。银行流水同样由 `(企业编号, 流水编号)` 定位。
- 用途为空或只有空白字符，视为未填写。**备注不能代替用途**。不能根据销售方名称或票面项目推测用途。
- 导入后的当前数据与原始 Excel 分开管理，此后以程序保存的数据为准。

**规则选择**

- 先按企业、业务日期和启用状态筛出适用规则，再引用。
- 甲企业 9 月用 R002 **2.0 版**（每张必填）；1.0 版（≥1000 元必填）已停用，**不能作为依据**。
- 乙企业用 R003 1.0 版：≥1000.00 元必填，**等于 1000 也算**；低于门槛的空白不能列为不合规。
- 初赛只对 9 月做用途检查；8 月数据只用于金额查询。

**金额口径（R001）**

- 用 Decimal 或整数分计算，保留两位小数，单位为元。
- 查询成功但没有记录时合计为 0.00 并说明没有记录；**无权限或查询失败不能回答为 0**。
- 用户没有说清月份、前文也没有明确月份时，必须追问，不能默认取当前月。
- 发票与银行流水之间没有对应关系，不能凭同额、相近日期或相同交易方推断已付款。

**授权**

- 只查询或只询问规则，不算授权修改。
- **新开对话不代表获得修改授权**：上一会话留下的修改草稿不能自动执行，必须本轮用户明确要求保存。

**评分权重**：基础完成度 40%，AI 应用合理性 25%，问题理解 15%，后续完善空间 10%，创新性 10%。

**提交内容**：源码、依赖与启动说明、2–3 页设计说明（已完成与未完成功能、模型与程序分工、记忆与知识管理方式、一个自己的设计选择）、关键运行记录、≤5 分钟演示。演示要覆盖追问、更正、跨会话记忆和适用规则选择，并展示实际保存的数据和运行记录。不得提交密钥、虚拟环境或大体积依赖。

## 2. 模型与程序的分工（对应 25% 评分项）

| 由模型负责 | 由程序负责 |
|---|---|
| 理解用户意图、指代和更正 | 身份与权限（来自会话入口，模型不可写） |
| 决定下一步：查询、追问、调用哪个工具、何时结束 | 金额计算（Decimal）与月份筛选 |
| 从用户原话中提取要写入的用途、备注文本 | 适用规则解析：按企业、日期、状态给出有效规则 ID |
| 判断本轮用户是否明确要求保存 | 字段白名单、参数校验、发票唯一定位 |
| 组织自然语言回复，引用程序给出的规则版本 | 幂等写入、保存后回读核验、任务与待办状态更新 |
| 识别和登记用户明确提出的长期偏好 | 记忆的范围隔离、版本与删除，上下文预算与裁剪 |

设计理由写进设计说明：凡是可以确定性验证的事情都交给程序，模型只做理解和决策；这样做的直接效果是规则用错、金额算错、越权写入在结构上不会发生。

## 3. 架构

```text
入口（CLI 对话 / 演示网页）—— 选定 user_id、company_id，会话开始
        ↓
Harness 单轮循环（最多 N 步）
  1 加载任务记忆：该用户在该企业的未完成任务（≤1 个）与待办账本
  2 构建模型输入：系统约束 + 范围绑定 + 任务摘要 + 相关长期偏好 + 有效规则片段 + 最近对话
  3 调用模型（tool calling）→ 得到工具调用或最终回复
  4 守卫：范围注入、权限、字段白名单、参数校验、写入前置条件
  5 执行工具 → 结果写回上下文 → 回到 3
  6 结束：更新任务与待办，写入运行记录
        ↓
SQLite：invoices / bank_txns / rules / rule_versions / tasks / open_items /
        memories / operations / runs / run_steps
```

### 3.1 工具清单（模型可见）

| 工具 | 说明 |
|---|---|
| `query_invoices(month, invoice_ids?, only_missing_purpose?)` | 企业由会话注入，模型不能传入 |
| `query_bank(month, direction?)` | 只读 |
| `summarize_month(month)` | 程序计算发票总额、银行收入、银行支出，返回 Decimal 字符串 |
| `check_purpose(month)` | 程序按适用规则列出必填但未填的发票，返回所用规则 ID 和版本 |
| `search_rules(query, as_of?)` | 返回有效规则片段，并标明名称、版本、条款 |
| `update_invoice(invoice_id, purpose?, remark?, idempotency_key)` | 只允许这两个字段；保存后立即回读，返回前后差异与核验结果 |
| `remember_preference(text, scope)` / `list_memories()` / `forget_memory(id)` | 长期偏好的增、查、改、删 |
| `ask_user(question)` | 显式追问，作为本轮结束动作 |

月份必须是 `YYYY-MM` 格式；缺少月份时工具返回 `MISSING_MONTH`，交给模型追问，程序不自动补当前月。

### 3.2 记忆

| 类型 | 内容 | 范围键 |
|---|---|---|
| 任务记忆 | 目标、月份、待办账本（发票 ID → 待补、已保存待核验、已核验）、最近确认事实 | `(user_id, company_id)`，未完成任务唯一 |
| 长期偏好 | 用户明确要求记住的内容（称呼、回答格式、常查月份等） | 默认 `(user_id, company_id)`；用户明确指定时才放宽到 `(user_id, *)` |
| 对话历史 | 原文保存；上下文只取最近若干轮 | 会话 |

- 待办账本中的状态只有在回读核验通过后才会被划掉，不以模型的说法为准。
- 新会话会载入任务记忆和偏好，但**会把未执行的修改草稿标记为失效**，以满足“新开对话不代表授权”。
- 偏好更正或删除后，修订号递增，摘要重新生成，删除的原文不进入运行记录以外的任何地方。
- 偏好不能覆盖权限、规则或本轮用户指令。例如“以后用万元显示”与 R001“单位为元”冲突时，以规则为准并告诉用户。

### 3.3 知识库

- 表结构：`rule_id, version, name, company_scope, effective_from, status, body, clauses[]`
- CLI：`fh rules import|list|search|update|disable`。更新时新增一个版本；停用后该版本不能再被引用。
- 检索：按企业、业务日期、状态过滤，再用中文关键词或短语匹配，返回原文片段。不引入向量库。
- 回复中的规则引用必须是程序在本轮返回过的规则 ID 和版本；如果不是，在运行记录中标为异常（创新点候选之一）。

### 3.4 写入与核验

本轮用户明确要求 → 定位唯一发票（不唯一则追问）→ 权限检查 → 生成 `idempotency_key`（由会话、轮次、发票和内容哈希构成）→ 在事务中写入并记录 operation → 回读 → 比对 → 更新待办 → 回复。

- 重复提交同一 key 不会重复写入，直接返回已有结果。
- 回读结果不一致时标为失败，不报成功。
- 复赛预留：超时后按 key 查状态，重启时恢复未完成的 operation（初赛只留接口和数据字段）。

### 3.5 运行记录

每轮保存一条 `run`，包括：完整模型输入（messages 和工具定义）、选中的记忆 ID 与规则版本、每一步工具调用的参数和结果、写入前后的值、耗时、token 用量，以及最终回复。密钥只从环境变量读取，日志写入前再做一次过滤。

查看方式：`fh runs show <run_id>`，演示网页侧栏也能看到。

### 3.6 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 语言与服务 | Python 3.11+、FastAPI、Pydantic | 评委只需装 Python 即可运行 |
| 存储 | SQLite；导入脚本加重置脚本 | 当前数据与原始 Excel 分离，可一键回到初始状态 |
| Excel 导入 | openpyxl | 读取后转成 Decimal 和日期 |
| 模型 | `LLMProvider` 接口：OpenAI 兼容适配器（首选）与 Anthropic 适配器 | 评审时只需改环境变量就能切到主办方 Key |
| CLI | Typer | 用于对话、规则管理、运行记录查看和重置 |
| 网页 | React + Vite，构建产物提交到仓库，由 FastAPI 托管 | 评委不需要安装 Node |
| 测试 | pytest（确定性部分）+ 多轮评测 runner | 模拟数据测试与真实模型评测分开报告 |
| 平台 | Windows 与 Linux 都提供启动脚本（`.ps1` 和 `.sh`） | 用户的主机是 Windows |

## 5. 评测

- **确定性层（pytest）**：附录 A 全部断言，加上权限、同号跨企业、字段白名单、幂等和回读不一致等测试。每次提交都跑。
- **模型层（evals runner）**：附录 B 的多轮案例。每个案例断言三类内容：数据库最终状态、工具调用序列中的关键约束（例如没有调用 `update_invoice`）、回复中必须包含的事实（金额、发票号、规则版本）。回复的自然程度由人工抽查，单独报告。
- 每个案例用相同配置跑 3 次，报告通过数 / 总数和失败原因。记录模型标识、调用次数和 token 用量。
- 加分对比实验（选做一项）：**规则解析交给程序 vs 让模型自己挑规则**，指标是用错 R002 1.0 版的比例。这个实验和赛题的“用错规则”直接对应，成本也最低。

## 6. 演示脚本（≤5 分钟）

1. （0:00）以 U001 身份进入甲企业：“9 月发票、银行收支各多少？” → 9622.06 / 13000.50 / 7180.74，引用 R001。

3. “F002 用途写打印复印纸，F004 是出差住宿” → 系统追问或确认 → 保存 → 回读；同时展示数据库里的值。
4. 更正：“F004 不对，是客户接待住宿” → 更新并回读。
5. “记住：以后先给合计再列明细” → 关闭会话 → 新开会话，问“还剩哪些没处理？” → 用上偏好，列出剩余 3 张，不自动执行旧草稿。

7. 切换为 U002 查乙企业 → 拒绝访问，不回答 0。
8. 打开一条运行记录：完整模型输入、选用的记忆与规则、工具调用、写入前后对比。

## 7. 审查协议（GPT‑6.1 Sol）

每次送审的材料包：commit 标识、本次 diff 的范围、`pytest` 与 eval 的实际输出、相关运行记录 JSON、已知问题。

GPT 的输出：每条问题写明影响、文件和行号、复现步骤、修复方向，标注“已验证”或“待核实”；不写实现代码。审查记录放在 `docs/reviews/R{n}.md`，Claude 修复后在同一文件里登记关闭情况。

各轮重点：

- R1：工具契约和守卫能否挡住越权与错写；规则解析是否严格按企业、日期、状态；金额口径。
- R2：程序里有没有关键词或场景分支替代模型决策；跨会话授权；隔离；运行记录完整性。
- R3：对照第 1 节逐条核对是否满足；全新目录能否复现；有没有任何未经实际运行的结论。

## 8. 需要用户决定的事项

1. **开发期间用哪个模型 API。** Claude Pro 和 OpenAI Plus 订阅都不包含 API 额度。需要一个可用于运行时的 Key，可以是 Anthropic API，也可以是 DeepSeek、通义等 OpenAI 兼容平台。M1 不依赖模型，可以先开工；M2 开始就需要。
